# 다른 계열 모델 재서술 강건성 시험 — 실행 전 계획 (사전 등록 초안, 2026-10-18)

> 이 문서는 유료 재서술을 돌리기 **전에** 고정한다. 결과가 어떻게 나와도 공개한다. 아직 커밋하지 않은 초안이다.
> 도구: `scripts/eval_paraphrase.py` (제품 코드 `src/`는 동결 커밋 `ccf3b4d` 그대로). 결과 폴더: `C:/jettae/data/eval/paraphrase/`.

## 1. 왜 하나

신청서는 봉인 평가셋을 이렇게 적었다.

> 기준 런북 20개(공개 런북 번안·공공누리 국내 매뉴얼 중 이용조건 확인분, 기존 결함은 분모에서 분리)×연산자 8종(…2종 보류)×표현 3종(다른 계열 모델이 표·명시형·구어체로 재서술)×위치 2 ≈ 1,000건

실제 봉인셋은 다르다. 기준 런북은 생성기(`jettae-evalkit-gen/1.1.0`)가 만든 **합성 조직 20곳**이고, 문체 3종은 생성기의 **문장 틀**로 썼으며, LLM 재서술은 없다. 게다가 B(규칙 파서 + 그래프)는 **같은 생성기의 개발 분할(시드 7)** 을 보며 조정했다(`report.md` 15절). 그래서 B의 봉인 탐지율 96.5%에는 "생성기 문장에 익숙해서" 얻은 몫이 섞여 있을 수 있다.

이 시험은 한 가지만 묻는다. **같은 사실을 다른 계열 모델이 다시 쓰면, B가 여전히 같은 결함을 찾는가?**

## 2. 신청서 문구와 무엇이 같고 무엇이 다른가

| 항목 | 신청서 | 이 시험 | 같은가 |
|---|---|---|---|
| 기준 런북 | 공개 런북 번안·공공누리 매뉴얼 20개 | 생성기 합성 조직 20곳 그대로 | **다름** |
| 기존 결함 분리 | 기준 런북의 원래 결함을 분모에서 뺌 | 합성 조직은 결함 없는 상태로 만들어짐(정상 대조군으로 확인) — 해당 없음 | 다름(해당 없음) |
| 결함 연산자 | 8종 + 보류 2종 | 같음(활성 8종 + 봉인 2종) | 같음 |
| 표현 3종 | 다른 계열 모델이 표·명시형·구어체로 재서술 | 다른 계열 모델(OpenAI `gpt-6.1-sol`, 제품 추출은 Claude)이 **생성기 원문을 같은 문체로 고쳐 씀**. 중립 원문 하나에서 3종을 새로 만드는 방식은 아님 | 일부 |
| 위치 | 2 | 같음(앞/뒤) | 같음 |
| 규모 | ≈1,000건 | 180건 표본(봉인 1,320건 중) | 다름 |

따라서 결과를 인용할 때는 "봉인셋 표본 180건을 다른 계열 모델이 같은 문체로 고쳐 쓴 판본"이라고 적는다. "공개 런북 기반 봉인셋"이라고 쓰지 않는다.

## 3. 표본 180건 — 설계와 크기 근거

**설계(결정적, 스크립트 `stratified_sample`).** 조직 20곳 × 문체 3종 = 60칸마다 정상 대조군 1건 + 결함 사례 2건을 **같은 위치**에서 고른다. 칸 (조직 i, 문체 s)의 위치는 `POSITIONS[(i+s) mod 2]`, k번째 결함 연산자는 `ALL_OPERATORS[(2i+k+4s) mod 10]`.

- 결과: 활성 연산자 96건 + 봉인 연산자 24건 + 정상 대조군 60건. 연산자 10종이 각 12건(문체마다 4건, 앞 2·뒤 2), 조직마다 서로 다른 연산자 6종, 문체·위치 균형(앞 90 · 뒤 90). 표 문체 60건 중 조직 전체 표 배치 18건.
- 180건 모두 봉인 `manifest.json`의 사례 해시와 일치한다(동결 때 추가된 정책 기본값 두 줄을 빼고 비교, `sealed_set_recheck.py`와 같은 방식).

**크기 근거.**
1. 결함 사례마다 같은 조직·문체·위치의 정상 대조군(쌍둥이)이 표본 안에 있어야 대조군 보정 탐지율을 계산할 수 있다 → 60칸 × (대조군 1 + 결함 2)가 최소 구성이다.
2. 연산자별로 읽으려면 연산자당 10건 이상이 필요하다. 120건(칸당 결함 1건)이면 연산자당 6건이라 연산자별 해석이 안 된다.
3. 검정력: 표본 원문에서 B는 활성 96건 중 93건을 찾는다(아래 6장). 짝 비교에서 재서술 때문에 놓친 사례가 6건 이상이고 새로 찾은 사례가 없으면 McNemar 정확 검정이 p < 0.05가 된다 — 관문 통과분이 모두 남으면 약 6%p 이상의 하락을 잡는다. 문체별(활성 32건)로는 약 20%p 이상의 차이만 구분된다.
4. 정상 대조군 60건: 오탐 0/60이어도 95% 상한이 6.0%라, 재서술 때문에 오탐이 몇 %대로 늘었는지까지 말할 수 있다.
5. 비용: 재서술 1회 시도 약 $10(보수적 추정, 8장). 360건으로 늘리면 비용이 두 배이고, 관문 탈락이 많으면 얻는 정밀도는 그만큼 작다.

## 4. 재서술 요청 (프롬프트 `paraphrase-v1`)

- 모델 `gpt-6.1-sol`, OpenAI Responses API. 실데이터 연구에서 쓴 어댑터(`OpenAIResponsesLLM`) 그대로: 안전 머리말, nonce 경계 문서, JSON 스키마(`text` 한 필드), 스키마 실패 시 1회 재요청, `store=False`, 표본 파라미터 없음.
- 보내는 것은 런북 본문 하나뿐이다. 문서 id는 `runbook.md`, 제목은 비움 — 사례 id(연산자 이름이 들어 있음)는 보내지 않는다. 명부·카탈로그도 보내지 않는다(명부 정보가 본문에 덧붙지 않게).
- 지시 요지: 같은 문체 유지(표 / '- 항목: 내용' 목록 / 해요체 문단), 사실을 빼거나 더하거나 바꾸지 않기, 원문에 없는 사람·팀·연락 수단·시간·단계·'없음' 같은 말 덧붙이지 않기, 사람 호칭·이름·숫자·단위·서비스·시스템·위치·채널 이름은 원문 표기 그대로, `#`/`##` 제목 줄과 절 순서 그대로, 그 안에서는 문장 구조·어순·연결어·항목 순서를 적극적으로 바꾸기. 전문은 스크립트의 `paraphrase_instructions`.
- 응답 정규화는 줄바꿈 통일과 문서 전체를 감싼 코드 펜스 하나 벗기기뿐이다.
- 시도: 사례당 최대 2회. 재시도는 **관문 탈락일 때만** 한다(B 결과를 보고 다시 하지 않는다). 첫 시도 통과율과 최종 통과율을 모두 보고한다.
- 답을 받지 못한 요청(2026-10-18 추가, 결과 보기 전): 크레딧·키·속도 제한·네트워크로 요청이 답을 받지 못하면 시도로 세지 않고
  실행을 멈춘다. 그 사례는 기록하지 않으므로 다음 실행에서 다시 보낸다. 잘린 답·형식 오류·거부는 모델의 답이므로 시도로 센다.
  D/DR 단계도 같다(답을 받지 못한 사례는 `llm_results.jsonl`에 남기지 않고 멈춤). 전에는 이런 요청도 시도 1회로 기록돼, 크레딧이
  떨어지면 남은 사례가 2회씩 '실패'로 소진되고 관문 탈락(`llm_error`)으로 빠졌다.

## 5. 사실 보존 관문 (`gate-v1`) — 결정적, 모델 없음

재서술본을 원문·정답 명세와 비교해 아래 중 하나라도 걸리면 제외하고 사유별로 센다. 문장은 서비스 절·표 행·서비스 이름으로 시작하는 목록 항목 단위로 서비스에 배정한다.

| 묶음 | 검사 |
|---|---|
| 구조 | `#`·`##` 제목 줄이 같고 순서가 같다. 문체 유지: 표는 서비스마다 표 행, 명시형은 목록 항목(표 없음), 구어체는 표·목록 없는 해요체 문장 |
| 서비스별 집합 | 연락 수단 집합, 숫자+단위 집합(분·시간·%·초·건·ms·p95·5xx), 명부 인물 집합이 원문 같은 서비스와 같다 |
| 사실 존재 | 시스템·위치, 담당자 문장(담당·맡 + 담당자, 신고 문장 제외), 감지 문장과 호출 대상, 조치 문장, 승인 문장 안의 승인자, 승인 요구, 실행자, 신고 기관, 신고 시한(침해사고 문장은 침해사고 시한, 유출 문장은 유출 시한), 상향 대상 순서 |
| 결함 유지(대상 서비스) | 담당자 삭제 → 담당 문장 없음 · 상향 순환 → 상향 문장에 CTO 없음 · 승인자 삭제 → 승인 문장에 실행자 말고 사람·직함 없음 · 대체 채널 삭제 → 연락 수단 1종 · 롤백 삭제 → 조치·승인 문장 없음 · 상향 경로 삭제 → 상향 문장·상향 대상 없음 · 감지 삭제 → 알람·감지 단어 없음 · KISA 신고 삭제 → 침해사고·KISA 단어 없음 · 신고 시한 48시간 → 숫자·시한 검사로 48시간 유지 · 담당자 퇴사 → 명부가 결함을 담으므로 담당 문장 유지만 확인 |
| 명부 밖 인물 | 명부에 없는 이름(생성기 이름 풀, 성+이름+직급, 성+직급, 영문 별칭, 'OO님'), 명부에 없는 팀 이름 |
| 재서술 여부 | 원문의 12자 이상 문장·항목·표 행 중 50%를 넘게 그대로 남기면 "재서술 안 됨"으로 제외 |

**관문 자체 검증 (무료, 실행 완료 — `gate_selftest.json`).**
- V1 원문 그대로 넣기: 1,320건 중 1,320건 통과(관문이 원문을 잘못 거르지 않음).
- V2 결함을 되돌린 글(같은 순서로 결함 없는 조직을 렌더): 1,080건 중 1,080건 제외, 모두 연산자에 맞는 사유(예: 승인자 삭제 120건 전부 `defect_undone_approver`). 담당자 퇴사는 본문이 같아 제외.
- V3 표본 원문에 사실 하나만 바꾼 글: 명부 밖 인물 180/180, 숫자 변경 180/180, 채널 추가 180/180, 감지 문장 삭제 180/180 제외.
- 손으로 쓴 재서술 3건(문체당 1건, 관문 시험용일 뿐 측정 자료 아님): 3건 모두 통과. 그중 결함을 되돌리거나 사실을 바꾼 변형 8건은 8건 모두 제외.

**알려진 한계.** 상향의 "몇 분 → 누구" 짝은 보지 않는다(시간 집합과 대상 순서만 본다). 키워드 목록 밖의 말로 쓴 사실은 "빠짐"으로 판정한다 — 통과를 줄이는 쪽(보수적)이다. 명부 밖 인물 탐지는 규칙 기반이라 모든 경우를 잡지는 못한다. V2·V3와 손 재서술은 관문 개발자가 만든 시험이라, 실제 LLM 재서술에서의 오판율은 결과의 탈락 사유를 사람이 표본 검토해야 알 수 있다(9장).

## 7. 평가와 해석 규칙 (결과 보기 전 고정)

**주 지표.** B 활성 탐지율 — 관문을 통과한 같은 사례의 원문 대 재서술본, 짝 비교(McNemar 정확 검정, 양측).

**보조 지표.** 봉인 탐지율, 대조군 보정 탐지율, 정상 대조군 오탐률(문체별), 연산자별·문체별 탐지율, 필드 정밀도/재현율/F1, 누락 필드 환각률, 근거 없는 요소, 인젝션 가드가 격리한 문서 수, 관문 통과율(첫 시도·최종)과 탈락 사유, 재서술 모델이 결함을 되돌린 비율(연산자별), 명부 밖 인물을 만든 비율, 관문에서 빠진 사례의 원문 B 탐지(제외가 B에 유리했는지 확인).

**선택(유료).** D·DR(`claude-sonnet-5-5`, effort medium — 2×2와 같은 추출 모델)을 통과 사례의 원문과 재서술본에 돌려 짝 비교. D와 DR은 사례마다 추출 1회를 공유한다.

**해석 규칙.**
1. 재서술본 수치는 "관문을 통과한 재서술"에 대한 값이며, 언제나 관문 통과율과 함께 인용한다.
2. 재서술 활성 탐지율이 같은 사례 원문보다 **5%p 이상 낮고 p < 0.05**면 "봉인 B 수치에는 생성기 문체 익숙함이 섞여 있다"고 적고, 신청서·발표의 B 수치 옆에 재서술 수치를 함께 적는다.
3. 그렇지 않으면 "다른 계열 모델이 같은 문체로 고쳐 쓴 판본에서 유의한 하락 없음(관문 통과 n건)"까지만 적는다. "실제 문서로 일반화된다"고 쓰지 않는다.
4. 최종 관문 통과율이 50% 미만이면 "재서술 시험 불충분"으로 보고하고 수치는 참고값으로만 쓴다.
5. 10/14에 공개한 봉인 수치(A·B·O)는 바꾸지 않는다.
6. 재서술을 시작한 뒤에는 표본·지시문·관문·평가 코드를 바꾸지 않는다. 바꿔야 하면 버전(`paraphrase-v2`, `gate-v2`)을 올려 처음부터 다시 돌리고 두 결과를 모두 공개한다.

## 9. 실행 명령

```powershell
$py = "C:/Users/euihak/.venvs/jettae-ops/Scripts/python.exe"
& $py -X utf8 scripts/eval_paraphrase.py --dry-run                           # 무료: 표본·관문 검증·B 기준선·추정
```

`--yes`와 `--max-usd`가 없으면 유료 단계는 추정만 출력하고 호출하지 않는다. `--max-usd`는 결과 폴더의 단계별 누적 상한이다(`spend.json`). 결과를 본 뒤 관문 탈락 사유를 사람이 20건쯤 무작위로 읽어 관문이 정상 재서술을 부당하게 거른 비율을 적는다.

## 10. 신청서와 남는 차이, 그리고 공개 런북으로 다시 만들기 어려운 이유

이 시험을 해도 신청서 문구와 남는 차이:
- 기준 런북은 여전히 합성 조직이다. 사람·팀·연락 수단·문장 구성이 생성기의 분포를 따른다.
- 재서술은 생성기 원문을 입력으로 받으므로, 원문의 정보 배치(절 구성, 한 절에 담긴 사실 묶음)는 그대로 남는다. 실제 사내 문서의 빠진 맥락·모호한 지시·서식 혼란은 재현하지 않는다.
- 관문을 통과한 재서술만 평가하므로, "사실이 흐트러진 문서"에서의 성능은 이 시험이 말하지 않는다.

**공개 런북 번안·공공누리 매뉴얼로 봉인셋을 다시 만드는 것이 남은 10일 안에 어려운 이유.**
1. **정답이 구성으로 정해지지 않는다.** 지금 봉인셋의 정답은 명세에서 나온다. 공개 문서를 기준으로 쓰려면 문서마다 담당·상향·승인·채널·롤백·감지·신고 문장을 사람이 표시하고, 그것을 명부·카탈로그와 이어 줘야 한다. 공개 런북에는 이름 있는 사람과 명부가 없다(GitLab 런북은 역할·채널 이름 위주). 명부를 지어내면 그 부분은 다시 합성이다.
2. **연산자 대부분을 걸 대상이 없다.** 공공누리 국내 매뉴얼은 대개 기관 공통 지침·서식이라 서비스별 담당·상향·승인 문장이 없다. 담당자 퇴사·상향 순환·대체 채널 삭제처럼 명부와 경로가 필요한 연산자는 적용할 수 없다.
3. **이용조건.** 공공누리 제3·4유형은 변경금지라 결함 주입(내용 변경) 자체가 이용조건에 어긋난다. 1·2유형만 쓸 수 있고, 문서마다 유형을 확인해야 한다.
4. **"기존 결함 분리"에는 사람 판정이 필요하다.** 실증 ①에서 두 LLM 코더(Claude·OpenAI)의 판정 일치가 κ 0.70 수준이었다. 기준 문서의 원래 결함을 2인이 판정·조정하려면 문서당 몇 시간이 든다.
5. **일정.** 남은 10일에 10/22 사람 검토, 2×2 본 실행, 발표 준비가 겹친다.

**가능한 축소 설계(하려면 별도 결과로).** 이미 MIT 라이선스로 충실 번역·검증한 GitLab 런북 test 20건 한국어판(`C:/jettae/data/real/gitlab-runbooks-ko`)을 기준 문서로 쓴다. ① 담당·상향·롤백·감지 문장이 실제로 있는 문서를 사람이 골라 문장 위치를 표시(예상 8–12건, 1인 약 1일), ② 두 번째 사람이 검수(0.5일), ③ 문장 삭제형 연산자 4종(담당·상향·롤백·감지 삭제)만 적용하는 스크립트(0.5일), ④ 기준 문서와 주입 문서를 같은 조건으로 돌려 **기준 문서에서 이미 나던 지적은 빼고 새로 생긴 지적만** 탐지로 센다(신청서의 "기존 결함 분리", 0.5일). 합계 약 2.5–3인일. 비용은 B 무료, D는 기준 + 주입 약 50회로 수 달러 수준(실증 ① 한국어판 20건 실행이 코더 포함 $0.70). 한계: "번안"이 아니라 "번역"이고, 명부가 없어 퇴사자·순환·대체 채널 연산자는 빠지며, 정답은 사람 표시라 봉인셋과 성격이 다르다 — 봉인셋 수치와 합치지 않고 따로 보고한다.
