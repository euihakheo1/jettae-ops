## 1. 지금 제품에서 이 KPI가 뜻할 수 있는 것

제품 구조를 먼저 적습니다(코드 근거: `src/jettae/improve/*`, `src/jettae/orchestrator/{service,pipeline}.py`,
`src/jettae/api/routers/patches.py`, ADR-0003).

| 제품에 있는 것 | 제품에 없는 것 |
|---|---|
| 끊김마다 고정 템플릿이 수정안(그래프 연산 + 한국어 문장)을 결정적으로 만든다(`TemplateDrafter`). 상향 대기시간은 등급별 고정 제안(1등급 5분·2등급 10분·3등급 30분), 사람은 명부 후보를 고정 순위로 고른다 | 승인·거절 이력에서 규칙을 배워 다음 초안을 바꾸는 기능(모델 재학습도, 규칙 추론도 없음) |
| 재검사·리허설 무회귀·명부 외 인물 0을 통과한 수정안만 '검증 통과'가 되고(`validate_patch`), 팀 리드·관리자만 승인한다(`VersionService.approve`) | 사람이 수정안의 내용(대기시간·사람)을 고쳐 승인하는 API·화면 |
| 승인하면 새 그래프 버전(append-only, 되돌리기도 새 버전)이 생기고 같은 그래프로 다시 판정·리허설한다 | 거절 사유를 기억해 같은 초안을 다시 내지 않는 기능(사유는 감사 로그에만 남음) |
| 런북을 고쳐 다시 진단하면 승인된 수정안만 새 추출 그래프에 다시 얹는다(`rebase_graph`, 감사 로그의 승인 계보) | 제품이 끊김으로 찾지 못한 조항을 수정안으로 넣는 길(검증이 '해소한 끊김 1건 이상'을 요구) |

그래서 측정할 수 있는 뜻과 없는 뜻을 나눕니다.

1. **측정 가능 — 승인분의 적용(다음 리허설에 자동 적용).** 숨은 규칙에 맞는 승인 기록이 있는 서비스에서, 기록·검증에
   한 번도 쓰지 않은 보류 시나리오를 돌렸을 때 제품 그래프의 실행이 정답 그래프의 실행과 같은가.
2. **측정 가능하지만 '복원'이 아님 — 기록 없는 서비스.** 같은 규칙 범위인데 기록이 없는 서비스의 실행 동치는, 제품이
   배우지 않으므로 기록 전 그래프 그대로입니다. 열린 초안을 그대로 승인했다고 가정한 값도 같이 재지만, 그것은 템플릿
   기본값이 규칙과 우연히 같은 정도입니다. 이를 확인하려고 기록 전후 초안이 같은지(학습이 없는지)를 셉니다.
3. **측정 가능 — 적용 범위 과대/과소.** 정답 그래프와 규칙 적기 전 그래프의 사실 차이(필요한 변경)와 제품 그래프의 사실
   차이(실제 변경)를 비교합니다(`evalkit.facts.graph_facts` 사실 보기). 범위 밖 서비스의 변경과 실행 변화도 셉니다.
4. **측정 가능 — 미승인 변경의 그래프 반영(목표 0건).** 편집자·열람자 승인, 검증 전 초안, 검증 실패(명부 외 인물) 수정안,
   거절된 수정안, 옛 버전 기준 수정안, 중복 승인, 편집자 되돌리기를 시도하고 그래프가 움직이지 않는지 봅니다. 또 모든 버전을
   승인된 수정안의 연산만으로 다시 만들어 최신 그래프와 같은지 확인합니다(이력 재구성).
5. **새 기능이 있어야 측정 가능 — 진짜 '숨은 규칙 복원'(일반화).** 승인 기록에서 규칙을 추론해 기록 없는 서비스에 제안하는
   기능이 생기면, 위 2번의 '열린 초안을 그대로 승인했다면' 계산이 곧 그 기능의 평가가 됩니다. 제품이 동결이라 만들지
   않았습니다.

## 2. 설계

- **조직**: evalkit 정답 생성기 20곳(시드 20261012, 봉인 평가셋과 같은 조직 명세). 런북은 표 문체로 렌더링.
- **숨은 규칙 3개**(제품에 주지 않음):
  - `pay-5m-lead` — 결제·정산·과금 계열: 1차 담당 5분 무응답 → 그 팀 팀장 상향, 롤백·페일오버 승인자는 팀장 한 명.
  - `reg-10m-lead` — 규제 대상 서비스: 1차 담당 10분 무응답 → 그 팀 팀장 상향.
  - `t1-two-approvers` — 1등급 서비스: 롤백·페일오버 승인자는 팀장과 CTO 두 명.
  - 규칙마다 '규칙 적기 전' 명세(해당 조항이 런북에 없음 → 제품이 끊김으로 찾음)와 '정답' 명세(조항이 적힘)를 만들고,
    두 명세의 오라클 그래프를 각각 G0·G*로 씁니다. 범위 밖 서비스는 두 명세에서 같습니다.
- **기록 서비스 / 기록 없는 범위 서비스**: 조직 안의 규칙 범위 서비스를 이름순으로 놓고 짝수 번째(0, 2, …)를 기록 서비스,
  홀수 번째를 기록 없는 서비스로 둡니다. 범위 서비스가 하나뿐인 조직은 기록 서비스만 있습니다.
- **팀장 시뮬레이션(4개 팔)** — 모두 `JettaeService.draft_patches/approve_patch/reject_patch`(API 라우터가 부르는 함수)로 진행:
  - `none`: 아무것도 승인하지 않음(G0 그대로) — 기준선.
  - `approve_all`: 규칙을 모르는 팀장이 검증 통과 초안을 전부 승인 — 템플릿 기본값이 규칙과 얼마나 같은지.
  - `rule_review`: 규칙을 아는 팀장이 기록 서비스의 초안만 보고, 그래프를 정답 쪽으로만 바꾸는 초안(추가 사실이 모두 정답에
    있고, 지우는 사실이 정답에 없는 것)은 승인, 나머지는 거절(사유 기록). **현재 API로 할 수 있는 사람 수정.**
  - `rule_edit`: `rule_review` + 거절한 서비스에 대해 팀장이 규칙대로 직접 고친 수정안(작성자 HUMAN)을 만들어 같은 검증을
    거친 뒤 같은 승인 함수로 승인. 도메인 모델은 지원하지만 **API·화면에는 없는 경로**라 상한으로만 봅니다.
- **보류 시나리오**: 서비스마다 사람 작성형 훈련 7종(1차 담당 20분 부재, 1차 담당 부재+목표 30분, 팀장 부재, 1차 담당 부재+사내
  메신저 다운, 1차 담당·팀장 동시 부재, 팀장·CTO 동시 부재, 규제 대상이면 침해사고+1차 담당 부재). 기록·검증이 끝난 뒤에야
  워크스페이스에 저장하고 `JettaeService.rehearse`(다음 리허설과 같은 경로)로 돌립니다. 정답 그래프에서 만든 제품 템플릿
  시나리오도 따로 셉니다.
- **실행 동치**: 결과(통과/실패), 완화 시각, 목표 시간, 실패 요소·위치, 사건 열(시각·종류·행위자·대상·연결) 전부가 같을 때.
  통과/실패만 같은 비율도 따로 적습니다.
- **적용 범위**: 사실 단위로 필요/맞게 반영/과소/과대(다른 값 포함)/범위 밖 변경. 사실 보기에 없는 노드 속성 변경(예: 롤백의
  '승인 필요' 명시값)은 따로 셉니다.
- **진단 경로(런북 추출 포함)**: 같은 규칙·조직으로 런북을 제품이 직접 진단(규칙 파서, LLM 끔)해 기록을 만들고, 기록과 무관한 줄(첫
  서비스 알람 지연 분)을 고쳐 다시 진단합니다. 승인분이 새 추출 그래프에 다시 얹히는지, 거절 내용이 들어가지 않는지, 거절한 초안이
  다시 제안되는지 봅니다. 정답도 정답 런북을 제품이 진단한 그래프입니다.
- **덤**: 템플릿 초안(LLM 끔)의 재검사 통과·명부 외 인물 수, 같은 초안을 AI가 다시 쓸 때의 요청 수·비용(오프라인 계산).

## 3. 해석 규칙

- 기록 서비스의 동치가 높아도 "규칙을 복원했다(배웠다)"고 쓰지 않습니다. "승인한 수정이 이후 처음 보는 리허설에도 그대로
  적용됐다"고 씁니다.
- `rule_review`(현재 API)와 `rule_edit`(API에 없음)의 차이는 "사람이 수정안을 고칠 수 없어서 생기는 손실"로 그대로 공개합니다.
- 기록 없는 서비스의 값은 학습이 아니라 템플릿 기본값의 우연 일치로 설명합니다.
- '범위 밖 참고'(저장소 직접 변조)는 API 경로가 아니므로 0건 KPI에 넣지 않되, 결과를 숨기지 않고 따로 적습니다.
- 규칙 아는 팀장 두 팔(`rule_review`·`rule_edit`)의 과대 0은 가상 팀장의 승인 기준('정답 쪽으로만 바꾸는 초안만 승인') 때문에
  구조상 0입니다. 제품의 성질로 쓸 수 있는 것은 '승인한 수정안의 연산 말고는 그래프에 들어가지 않는다'(이력 재구성 위반 0)까지입니다.
  규칙을 모르는 팀장이 전부 승인하면 과대가 생깁니다(`approve_all` 과대 49).
- 범위 밖 서비스 그래프 변경 0/131은 합성 조직의 범위 밖 서비스가 처음부터 끊김이 없어 초안이 나오지 않았기 때문이기도 합니다
  (`approve_all`도 0). "규칙 범위를 알아서 지킨다"가 아니라 "끊김이 없는 서비스는 건드리지 않는다"로 씁니다.

## 5. 발표·질의응답용 공개 문구

## 6. 유료 실행이 필요한가

이 KPI에는 필요 없습니다. 수정안의 그래프 연산은 언제나 코드가 만들고, LLM은 문장을 다시 쓰고 같은 명부 후보 중에서 고를 뿐이며
승인·거절 기록을 보지 않습니다. LLM을 켜도 '기록에서 배우지 않는다'는 결론은 바뀌지 않습니다. 신청서의 다른 줄인 'AI 수정 초안
재검사 통과율·명부 외 인물 생성'은 LLM 초안 경로라 유료이고, 별도 스크립트 `scripts/eval_patch_recheck.py`(같은 날 작성,
`--llm --yes --max-usd`가 있어야만 유료 호출)가 다룹니다. 참고로 `scripts/eval_hidden_rule.py`가 요청을 보내지 않고 센 AI 첫 초안 요청은 숨은 규칙 사례
112회, 봉인셋 결함 200종(조직×연산자) 오라클 그래프 114회이고, 정가로 각각 약 $2.80(claude-sonnet-5-5, 호출당 출력 상한
2,000토큰 가정)입니다.
