# SSH MaxStartups 초과 가능성

<https://gitlab.com/gitlab-com/gl-infra/production-engineering/-/issues/7168>에서 이것이 필요하다는 것을 발견하게 된 맥락을 확인할 수 있습니다.
이 문서가 너무 간략하다면, 자세한 내용은 그쪽을 참고하세요.

## 조치 방법

*다른* 무언가가 터지고 있지 않은지 확인합니다.
이 경보는 데이터베이스 장애 같은 다른 주요 이벤트가
ssh 인증이 완료되지 못하게 막고 있을 때 발생할 수 있습니다(예: DB에서 ssh 키를 조회할 수 없음).
다른 문제가 진행 중이라면, 이 경보에 대해서는 더 이상의 별도 조치가 필요하지 않습니다.

다른 것이 터지고 있지 않다면,
이 경보는 MaxStartups 한도가 초과되어 git+ssh 연결이 드롭되고 있음을 시사합니다.
참고로 이 경보의 기준이 되는 메트릭은 HAProxy 로그에서 도출된 것이며
근본 문제에 대한 대리 지표이므로, 앞으로 오탐이 발견될 수도 있습니다.
향후(Ubuntu 18.04)에는 openssh에서 더 나은 로그를 얻을 수 있는데,
이 로그는 이 현상이 발생할 때 명시적으로 알려 줄 것이므로, 대신 그것을 기준으로 경보를 걸 수 있습니다.
하지만 이 한도에 얼마나 근접했는지를 실제로 발생하기 *전에* 볼 수 있을 거라는 기대는 없습니다.
openssh에 일종의 통계 내보내기 기능을 넣는 데 성공하지 않는 한 말입니다(잘해야 희박한 가능성입니다).

**긴급도:** 이 문제를 꾸준히 잘 관리해 왔다면, 긴급도는 낮지만 모니터링은 중요합니다.
임계값을 처음 넘기 시작할 때 경보를 받게 되어 있으며, 그 시점에는 고객 영향이 아직 낮습니다.
제 예상으로는 이 현상이 다시 발생하기 시작하면,
매시 정각에 발생하는 것을 보게 될 것이고, 아마 피크 때 하루 두어 번 정도에 그칠 것입니다.
발생에 아주 약간이라도 패턴이 보이면,
설정을 변경할 때, 즉 SSH 설정의 MaxStartups 값을 올릴 때가 된 것입니다.
`k8s-workloads/gitlab-com`의
[`releases/gitlab/values/values.yaml.gotmpl`](https://gitlab.com/gitlab-com/gl-infra/k8s-workloads/gitlab-com/-/blob/master/releases/gitlab/values/values.yaml.gotmpl)에서,
`gitlab.gitlab-shell.config.maxStartups` 설정을 조정합니다. `start`와 `full` 숫자를 늘려야 합니다:

- `start`는 인증 전 연결을 드롭하기 시작하는 수준이며, 우리가 도달하고 있다고 의심하는 값이 바로 이것입니다.
- `full`은 모든 새 인증 전 연결이 드롭되는 수준이므로, 첫 번째 값보다 어느 정도 더 커야 합니다;
   지금까지는 +50을 사용해 왔고, 아마 그 정도면 충분할 것입니다.  여기서의 목표는 연결을 너무 빨리 너무 가혹하게 다루지 않는 것입니다.
- `rate`는 첫 번째와 두 번째 한도 사이에서 연결의 몇 퍼센트를 무작위로 드롭할지를 나타냅니다; 30%면 괜찮으니,
   그대로 두어도 됩니다.  우리의 목표는 연결을 *하나도* 드롭하지 않는 것이므로,
   이상적으로는 이 값이 큰 차이를 만들지 않습니다(여기서 경보 대상인 드롭 중 첫 번째 드롭을 유발하는 것 외에는).

이 글을 작성하는 시점에서 값은 `250:30:300`입니다;
낮은 쪽 숫자는 시행착오를 거쳐 결정되었으며([이슈](https://gitlab.com/gitlab-com/gl-infra/production-engineering/-/issues/7168) 참고,
해당 작업이 진행된 곳), 오류가 사라지는 지점까지 값을 늘렸습니다.
안타깝게도 (위에서 언급했듯이) 현재로서는 이 한도에 도달하기 전에 얼마나 근접했는지 미리 확인할 방법이 없으므로,
향후 값을 다시 낮추는 것은 위험합니다.
이는 그러한 관측성을 확보할 때까지는,
이 값을 큰 폭으로 늘려서는 안 된다는 뜻입니다(예: 인시던트 한 번당 < 50% 증가를 제안합니다)

커밋, 푸시, 머지하고 Helm 차트를 적용합니다.

**한도:** 알 수 없지만, 이 숫자를 늘렸을 때 알려진 유일한 직접적 영향은 약간의(상당히 작은)
초기 단계 연결을 유지하기 위한 ssh 서버의 메모리 사용량입니다;
기본값은 `10:30:100`이었고, 현재 그보다 훨씬 높지만 무언가가 부정적인 영향을 실제로 감지한 적은 없습니다.
물론 더 큰 숫자(수만~수십만)는 흥미로운 결과를 낼 수도 있습니다
TCP 처리 측면에서 말이죠. 하지만 거기까지 갈 것으로는 예상하지 않습니다.
직감적으로는 1000을 넘어가면 조금 경계하겠지만, 괜찮다는 것을 관찰하고 측정할 수 있다면 마음껏 하세요.
이 값이 높을수록, 우리 git 서버가 동시에 처리해야 할 것으로 예상되는 연결이 많아집니다
연결이 인증을 마치는 시점에 그렇습니다. 그리고 인증에는 API 호출과 DB 작업이 필요하므로,
값을 올릴 때마다 그 전후로 git 서버의 CPU와 부하를 주시하세요.
감당할 수 없게 되면, git 서버를 더 늘려야 할 가능성이 높으며,
그러면 각 서버가 처리하게 될 연결 수가 암묵적으로 줄어듭니다.

## 추가 맥락

이 경보는 민감한/공격적인 경보(낮은 임계값, 짧은 기간)인데, 우리가 감지하려는 문제가 매우 짧고 순간적으로 치솟는 형태이기 때문이기도 하고,
정상적인 상황에서는 절대 발생해서는 안 되며 이를 제어하기 위해 당길 수 있는 레버도 충분하기 때문이기도 합니다.
가장 확실한 것은 MaxStartups(위 참고)이지만, `roles/gprd-base-haproxy-main.json`의 `rate-limit sessions`를 낮게 조정하여
초당 SSH로 전달되는 연결 수를 제어할 수도 있습니다.
참고할 자료는 <https://gitlab.com/gitlab-com/gl-infra/production-engineering/-/issues/7168#note_191678023>
및 <https://gitlab.com/gitlab-com/gl-infra/production-engineering/-/issues/7168#note_193486226>이며,
여기에 이 계산에 대한 논의가 담겨 있습니다.  하지만 이 값을 너무 많이 낮추면 사용자 경험에 부정적인 영향을 주며,
MaxStartups는 당기기에(늘리기에) 훨씬 저렴하고 안전한 수준입니다.

이 경보의 메트릭은 HAProxy 노드의 mtail에서 나오며, 'termination_state'가 'SD'이고 bytes_read가 `0` 바이트인
SSH 연결(git 프런트엔드 서버로의 연결)을 집계하는데, 이는 MaxStartups 초과를 나타내는 좋은 대리 지표입니다.
