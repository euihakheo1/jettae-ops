# 규칙 밖 위험 탐색 (EXPLORE_V1)

> 고정 규칙 35개는 정해진 질문에만 답합니다. 규칙이 묻지 않는 위험은 **자동 전수 탐색과 생성형 AI가 가설로 제안**하고,
> **결정적 리허설이 확인·기각·확인 필요를 정합니다.** 가설은 준비도 점수·끊김 판정·통과 기준(`--fail-under`)에 반영하지 않습니다.

## 1. 왜 있는가

"규칙 35개로는 규칙 밖의 위험을 못 찾지 않나?"라는 질문에 대한 답입니다. 고정 규칙은 판정의 기준이라 공개되고 바뀌지
않아야 하지만(설계 원칙 P1), 그만큼 묻는 것이 정해져 있습니다. 예를 들어 단일 장애점 규칙(`JT-SPF-001/002`)은
"이 사람(이 채널) **하나만** 빠지면 끊기는가"를 묻습니다. 다음은 묻지 않습니다.

- 각자는 대신할 사람이 있는 **두 사람이 함께** 빠질 때 (연휴, 같은 출장)
- 서로 다른 것처럼 보이는 **연락 수단 두 개가 함께** 멈출 때, 또는 한 센터 장애로 함께 멈출 때
- **다른 서비스 장애와 겹쳐** 같은 사람이 그쪽 1차 대응에 불려 갈 때
- 대체 경로는 적혀 있지만 상향 시점·응답 순서 때문에 **목표 복구 시간 안에 닿지 않을 때**
- 어떤 입력에도 적히지 않은 **공통 의존**(예: 메신저와 인터넷 전화가 같은 사내망)

## 2. 구조 — 제안과 판정을 나눈다

```
고정 규칙 35개 ──────────────→ 끊김·준비도 점수·통과 기준 (탐색과 무관하게 그대로)
      │ 이미 보고한 조합은 다시 싣지 않음
      ▼
자동 전수 탐색 (LLM 0회) ──┐
생성형 AI 제안 (선택) ─────┼─→ 가설 ─→ 결정적 리허설(서비스 목표 복구 시간) ─→ 확인됨 / 기각 / 확인 필요
이전 진단의 AI 가설 ───────┘
```

- 진단 파이프라인에서 `rehearse → explore → draft` 순서로 돕니다(LangGraph 노드 `explore`). 승인·되돌리기 뒤의 재판정
  (`evaluate_graph`)도 같은 탐색을 LLM 없이 다시 돌리고, 이전 진단의 AI 가설은 새 그래프에서 다시 확인합니다.
- 리허설을 끄면(`--no-rehearse`, `DiagnosisOptions(rehearse=False)`) 판정할 수단이 없으므로 탐색도 돌지 않습니다.
  `DiagnosisOptions(explore=False)`로 탐색만 끌 수 있습니다.
- 구조로 보장하는 것(import-linter 계약, CI에서 강제):
  - `jettae.explore.sweep`·`verify`·`drafts`는 LLM 클라이언트를 import할 수 없습니다(판정 경로 LLM 0회).
  - `jettae.check`·`rehearse`·`improve`·`extract`·`reporting`은 `jettae.explore`를 import할 수 없습니다 —
    가설이 끊김·점수·리허설 판정·수정안 검증에 섞여 들어갈 길이 없습니다.

## 3. 자동 전수 탐색 (LLM 0회)

핵심 서비스(정책의 `critical_tiers`)마다 다음 순서로 찾습니다.

1. **기준 리허설.** 교란 없이 재생해 이미 실패하면 탐색하지 않습니다. 고정 규칙이 그 끊김을 이미 보고했고, 어떤
   조합이든 "끊긴다"고 나와 의미가 없기 때문입니다. 제외 사유는 리포트에 남습니다.
2. **탐색 대상.** 그 서비스의 대응이 실제로 기대는 것만 봅니다.
   - 대응 경로 계보(`jettae.check.spof.response_lineage`)의 사람·연락 수단: 담당, 호출 대상, 상향 경로 전체, 승인자,
     그들의 연락 수단과 대체 채널 (명부상 재직 중인 사람만)
   - 그 연락 수단이 의존하는 시스템·위치(센터): 하나가 멈추면 리허설에서 그곳에 기대는 채널이 함께 멈춥니다
   - 1차 대응자를 공유하는 다른 핵심 서비스: 동시 장애가 나면 그 사람이 그쪽에 투입됩니다
   - 같은 효과를 내는 대상은 하나만 남깁니다(채널 하나만 둔 센터는 그 채널로 대신).
3. **이름이 아니라 효과로 비교.** 조합은 리허설에서 실제로 빠지는 사람·연락 수단으로 비교합니다. 센터·시스템 장애는
   그곳에 기대는 채널들이고, **동시 장애는 그 장애가 끌어가는 사람**입니다. 리허설과 똑같이 "그쪽 1차 대응자 중 이
   조합에서 아직 빠지지 않은 첫 사람"으로 계산합니다. 그래서 동시 장애가 이미 다룬 사람의 부재와 효과가 같으면 따로
   싣지 않습니다. 예를 들어 상품 카탈로그 동시 장애는 박재현 팀장 부재와 같습니다. 별빛상점에서는 모든 동시 장애가
   이런 경우라, 동시 장애가 들어간 가설은 나오지 않습니다.
4. **최소 조합.** 대상 하나씩, 그다음 둘씩 조합해 재생합니다. 목표 시간은 **서비스의 정책 목표 복구 시간**입니다.
   이미 끊기는 조합의 효과를 모두 포함하는 조합과, 이미 재생한 조합과 효과가 같은 조합은 건너뜁니다. 그래서 실린
   조합은 모두 **최소**입니다(어떤 부분 조합도 끊지 않음). 효과가 같은 조합이 둘이면 사람·채널을 직접 가리키는 쪽을
   남깁니다.
5. **규칙 우선.** 끊기는 조합의 대상이 모두 같은 서비스의 고정 규칙 판정에 이미 이름이 올라 있으면 가설로 다시 싣지
   않고 "이미 보고한 조합"으로만 셉니다. 동시 장애는 끌어가는 사람으로 바꿔서 봅니다. 예를 들면 크기 1인 `JT-SPF-001`
   단일 장애점, `JT-ESC-002` 상향 순환입니다.

설명 문장은 끊김의 성격을 나눕니다. 대신할 사람·연락 수단이 **구조적으로** 남지 않는 경우와, 구조상 대체 경로는
있지만 리허설에서 **시간·순서 때문에** 시한을 넘기는 경우(고정 규칙의 구조 검사로는 보이지 않음)입니다.

탐색 상한(EXPLORE_V1, `SweepLimits`). 상한에 걸리면 리포트에 한국어 줄로 남습니다(조용히 자르지 않음).

| 상한 | 값 | 넘으면 |
|---|---:|---|
| 조합 크기 | 2 (코드에서 3까지) | — |
| 서비스당 탐색 대상 | 20 | 기준 리허설 경로에 있는 대상부터, 종류·id 순으로 남김 |
| 실행당 리허설 | 1,500회 | 남은 서비스·조합을 탐색하지 못했다고 기록(기준 리허설도 못 돌린 서비스도 목록에 남김) |
| 서비스당 가설 | 12 | 작은 조합부터 남김 |
| 실행당 가설 | 60 | 작은 조합부터, 서비스 순서대로 남김 |

## 4. 생성형 AI 제안 (선택)

LLM이 켜져 있으면(LIVE·REPLAY) 탐색이 보지 못하는 현실적인 위험을 최대 3개(`llm_hypothesis_count`) 제안받습니다.
AI 리허설 시나리오와 같은 안전장치를 씁니다.

- **모델이 받는 것:** 코드가 만든 열거 목록만 — 확인된(판단 보류가 아닌) 노드 id(종류별), 대응 경로·의존 관계 엣지,
  핵심 서비스의 등급·목표 시간, 고정 규칙 판정(규칙 ID·서비스·대상 id), 탐색이 이미 찾은 조합. **런북 원문은 보내지
  않습니다.** 목록의 id는 데이터일 뿐 지시가 아니라고 지시문에 명시합니다.
- **모델이 하는 것:** 목록에 있는 id 중에서 고르기, 제목·설명 쓰기, 그래프에 없는 전제를 `assumptions`에 적기.
- **모델이 못 하는 것:** 상태·성공 여부·점수·목표 시간 정하기(스키마에 그런 칸이 없고, 있으면 응답 전체가 거부됨),
  시간 창 정하기(교란은 장애 내내 이어짐), 목록에 없는 대상 만들기.
- **검증:** 다음 중 하나라도 해당하면 그 제안 전체를 버립니다.
  - 서비스나 대상 id가 없거나, 판단 보류이거나, 종류가 맞지 않음(채널 다운에 사람)
  - 자기 서비스를 동시 장애로 고름
  - 교란이 4개를 넘거나 전제가 3개를 넘음

  글자는 정규화(제어·보이지 않는 문자 제거, NFC)하고 길이를 자릅니다.
- **중복:** 전제 없는 제안이 탐색이 이미 찾은 끊김 조합(규칙이 보고한 것 포함)으로 설명되면 새 위험이 아니므로
  버립니다. 같은 조합의 반복, 찾은 조합에 대상을 덧붙인 것, 이미 보고된 단일 장애점을 끌어가는 동시 장애가 여기에
  해당합니다. 비교는 3장과 같은 효과 기준입니다. 리포트에는 "중복이거나 이미 찾은 끊김 조합과 겹침 N건"으로 따로 셉니다. 요청
  개수를 넘은 정상 제안은 "요청 개수를 넘은 N건 제외(상한)"로 셉니다.
- **설명 표시:** 모델이 쓴 설명은 "AI 설명(검증하지 않음 — 리허설이 확인한 것은 '함께 일어나는 일'의 교란뿐입니다)"을
  붙여 싣습니다. 확인됨이어도 리허설이 확인한 것은 나열된 교란뿐이고, 설명 문장은 확인하지 않았습니다.
- **계량:** 호출은 작업 이름 `explore`로 따로 집계됩니다. 판정 경로 LLM 호출은 그대로 0회입니다.
- **AI 제안이 없는 이유:** 리포트에 경우별로 따로 적습니다.

  | 상태(`ai_status`) | 리포트 문구 |
  |---|---|
  | `off` | LLM 끔 / 녹화된 응답에 없는 요청 / LLM을 쓸 수 없음(자격 증명 없음 등) — LLM 모드로 구분 |
  | `failed` | 생성형 AI 제안 실패(사유는 아래 참고) — 자동 전수 탐색 결과만 실음 |
  | `fallback` | 추출 단계에서 LLM이 실패해 이 실행은 LLM을 더 쓰지 않음 |
  | `not_requested` | 제안 개수 0 또는 제안받을 서비스 없음 |
  | `rejudge` | 승인·되돌리기 뒤 재판정은 LLM을 쓰지 않음 |

  어느 경우든 탐색 결과는 그대로 싣습니다.

## 5. 검증과 상태

모든 가설(탐색·AI 공통)을 같은 결정적 리허설로 재생합니다. 가설의 교란을 장애 내내 적용하고, 목표 시간은 서비스 정책
값입니다. 같은 서비스를 교란 없이도 한 번 재생해 비교합니다.

| 상태 | 표시 | 조건 (위에서부터 적용) |
|---|---|---|
| `needs_info` | 확인 필요 | 교란 없이도 리허설이 실패함(가설만의 영향을 가를 수 없음), 서비스나 대상이 판단 보류(HOLD)임, 또는 그래프에 없는 전제(`assumptions`)가 있음 |
| `confirmed` | 확인됨(리허설로 재현) | 리허설이 실패함 |
| `refuted` | 기각 | 리허설이 목표 시간 안에 완화함 |

- 전제가 있는 가설은 리허설이 실패해도 **확인됨이 되지 않습니다**(확인 불가 ≠ 정상의 반대 방향: 확인되지 않은 전제로
  위험을 단정하지 않음). 무엇을 확인해야 하는지가 `required_info`에 "전제 확인: …"으로 남고, 전제를 반영한 재생 결과도
  함께 기록됩니다.
- 판단 보류(HOLD) 요소는 리허설이 쓰지 않으므로, 판단 보류 대상을 교란하면 리허설에서는 아무 일도 일어나지 않습니다.
  그 결과로 기각하거나 확인하면 확인되지 않은 사실로 판정하는 셈이라, 이런 가설은 **확인 필요**로 두고 "판단 보류 확인:
  …"을 남깁니다. 새 AI 제안은 판단 보류 id를 고를 수 없습니다. 이 규칙은 이전 진단에서 이어받은 가설이 재진단 뒤
  판단 보류가 된 대상을 가리킬 때 적용됩니다.
- 이전 진단에서 이어받은 AI 가설이 이번 탐색이 찾은 끊김 조합으로 설명되면 다시 싣지 않고 메모를 남깁니다. 결제처럼
  수정안 승인 뒤 처음 탐색되는 서비스에서 같은 조합이 두 줄로 실리는 것을 막습니다. 판단 보류 대상을 가리키는 가설은
  이 처리에서 빼고 위 규칙대로 확인 필요로 둡니다.
- 가설 id는 `hyp-` + 내용 지문(출처·서비스·사고 유형·교란·전제, 문구 제외)이라 같은 입력이면 실행마다 같습니다.

## 6. 어디서 보나

| 출력 | 내용 |
|---|---|
| 진단 JSON·REST API(`DiagnosisReport`) | `risk_hypotheses`(가설·상태·재생 결과·근거 원문), `exploration`(탐색 범위·제외·상한·AI 사용). 이전 보고서는 빈 목록·`null`로 읽힘 |
| 증적 리포트(Markdown·HTML) | **9장 「규칙 밖 위험 후보 (점수에 반영하지 않음)」** — 요약, 표, 확인됨·확인 필요 가설의 설명·리허설 기록·확인할 것·근거 원문. 가설이 없을 때 "찾지 못했습니다"는 모든 핵심 서비스를 상한 안에서 끝까지 탐색했을 때만 씁니다. 탐색하지 못한 서비스가 있으면 그 서비스는 확인하지 못했다고 쓰고, 하나도 탐색하지 못했으면 "확인하지 못했습니다"라고 씁니다 |
| `jettae scan`(텍스트) | 한 줄: `[규칙 밖 위험 후보] 확인됨(리허설로 재현) N건 · 확인 필요 M건 · 기각 K건` |
| `jettae scan --format json` | `summary.risk_hypotheses`(상태별 개수) + 전체 보고서 |

SARIF(코드 스캐닝 경고)에는 넣지 않습니다. 코드 스캐닝의 경고는 고정 규칙 판정만입니다. 웹 대시보드에는 아직 별도
패널이 없어, 증적 리포트·CLI·JSON·API로 봅니다.

## 7. 별빛상점 예시 (LLM 끔)

`examples/dmc-shop`을 그대로 진단한 v1과, 결선 데모에서 승인하는 결제 수정안 4건을 반영한 v5입니다. 점수·끊김은
탐색과 무관하게 각각 55.7점·38건, 66.4점·30건입니다.

**v1 (수정 전)** — 핵심 서비스 9개 중 4개 탐색, 리허설 97회, 확인됨 2건, 이미 보고한 조합 5개 제외

- 결제·배송·상품 카탈로그·이상거래 탐지·정산은 교란 없이도 리허설이 실패해 탐색하지 않았습니다. 결제는 담당이
  퇴사자(김민준)라 고정 규칙이 이미 끊김으로 보고합니다 — 규칙 밖 위험을 볼 단계가 아닙니다.
- **주문 · 정민혁 부재 + 슬랙 다운** → 확인됨. 정민혁 과장이 없으면 15분 뒤 최영훈 차장에게 상향되는데, 최영훈 차장의
  연락 수단은 슬랙 하나뿐이라 끊깁니다. 사람이 직접 쓴 리허설 S3(슬랙 장애 + 정민혁 연차)을 탐색이 스스로 찾은 것입니다.
- **주문 · 전화 다운 + 슬랙 다운** → 확인됨(담당 호출이 최영훈 차장에서 끊김).
- 제외(규칙이 이미 보고): 주문 한서윤 단독(`JT-SPF-001`), 주문 정민혁+최영훈(`JT-ESC-002` 상향 순환), 웹 프론트엔드·
  장바구니·환율의 박재현 단독(`JT-SPF-001`).
- 상품 카탈로그 동시 장애는 그쪽 1차 대응자인 박재현 팀장을 끌어가므로 박재현 부재와 같습니다. 웹 프론트엔드·장바구니·
  환율 롤백 승인자가 박재현 팀장 한 명이라 끊기지만, 이는 위 `JT-SPF-001`이 이미 보고한 단일 장애점이라 새 위험으로
  세지 않습니다.

**v5 (결제 수정안 4건 승인 후)** — 탐색 5개 서비스, 리허설 125회, 확인됨 4건(결제 2 + 주문 2), 이미 보고한 조합 5개 제외

- 결제가 기준 리허설을 통과해 탐색 대상이 되었고, 수정 뒤에도 남는 **둘이 함께 빠질 때의 위험** 2건이 확인됐습니다.
  - **결제 · 박재현 부재 + 한서윤 부재** → 롤백 승인이 한서윤에서 막힘(승인자와 대리 승인자가 함께 부재)
  - **결제 · 김서연 부재 + 한서윤 부재** → 담당 호출이 한서윤에서 끊김(1차 담당과 상향 대상이 함께 부재)
- 주문의 두 조합(v1과 같음)은 그대로 남습니다.
- 결제 2건은 고정 규칙으로는 끊김이 아니므로 점수(결제 100점)는 그대로입니다. 팀이 "둘이 함께 빠지는 날"을 운영 규칙
  (휴가 겹침 금지, 세 번째 승인자)으로 다룰지 판단할 근거입니다. 상품 카탈로그 동시 장애가 박재현 팀장을 끌어가는
  경우는 박재현 부재와 같아서 따로 싣지 않습니다.

## 8. 한계

- **탐색은 그래프에 적힌 의존만 봅니다.** 아무 입력에도 없는 공통 의존(같은 사내망·같은 건물)은 보이지 않습니다. 그런
  위험은 AI가 전제로 제안할 수 있지만 사람이 확인하기 전까지 **확인 필요**로 남습니다. 확인되면 카탈로그에 의존 관계를
  적으면 다음 진단부터 탐색이 직접 봅니다.
- **AI 가설은 검증 전까지 가설입니다.** 모델의 설명은 그대로 싣되, 상태는 리허설만 정합니다.
- **기각은 "그래프에 적힌 사실로는 대응이 이어진다"는 뜻**이지, 그 위험이 없다는 보증이 아닙니다.
- **점수에 넣지 않습니다.** 가설 수가 준비도 점수나 CI 통과 기준을 움직이지 않습니다(P1). 같은 조직이라도 가설을 늘리는
  만큼 점수가 내려가는 일이 없도록 의도한 것입니다.
- 탐색은 둘까지의 조합과 위 상한 안에서만 합니다. 동시 장애는 리허설의 공개된 단순화(1차 대응자 한 명이 장애 내내
  빠짐)를 따르고, 교란은 장애 내내 이어진다고 봅니다. 탐색은 서비스 장애(outage)만 다루고, 침해사고·개인정보 신고
  경로는 고정 규칙과 템플릿 리허설이 봅니다.
- 탐색 단계에 걸린 시간(개발 PC, 보고서 `timings_ms.explore`): 별빛상점 v1(전수 탐색 리허설 97회 + 검증)은 0.05~0.2초,
  v5(리허설 125회)는 약 0.2초였습니다. 테스트·데모 서버가 함께 돌 때는 0.4~0.9초까지 걸렸습니다.
