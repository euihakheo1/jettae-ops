# OSS & competitors (verified)

## lore: runbook compiler ("how did we fix this last time, and does it still work?") — get-h3 (GitHub org); v0.1.0 tag signed by 'totalwindupflightsystems' (GitHub, MIT, Python. Repo created 2026-09-23; annotated tag v0.1.0 dated 2026-09-24 (GitHub Release object published 2026-10-03); commits through 2026-10-11 (239 on main); 0 stars; not on PyPI)
https://github.com/get-h3/lore
- A CLI that compiles a fleet's incident history into one runbook per failure class. The README lists 13 curated classes plus an explicit 'unclassified' bucket, so an unknown symptom is not guessed at. The v0.1.0 tag message says 10 classes; the class count has grown since. Classification uses signature patterns and keyword scoring, not an LLM. `lore validate` re-runs each runbook's read-only checks: it plans by default and only executes with `--execute`, and it marks a drifted runbook 'stale' with a reason. `lore gate` follows propose-not-write for absorbing new lessons into runbooks: it writes nothing without `--record`, and a DENY never writes. `audit` produces a per-class matrix of status, check counts and freshness. Its stated rule is that missing data shows as 'no data', never as zero, and `last_validated` stays empty until a human attests. The README does not mention graphs or LLMs.
- JETTAE: Overlap: this is the 'runbook compiler' the founder referred to. It shares JETTAE's habits of saying 'I don't know' instead of inventing, gating writes on approval, and re-validating for staleness. Difference: lore compiles diagnostic commands out of incident history (the technical how-to). JETTAE compiles Korean free-text runbooks into an organisational response graph (owner, approver, deadline, notification channel, escalation) and checks whether that path closes. lore has no owner-absent or messenger-down rehearsal, no legal-deadline rules and no readiness score. Worth borrowing: render 'no data' rather than 0 inside the 0-100 score, and add a 'stale' flag when a contact or channel stops resolving. The repo has 0 stars and is about three weeks old, so cite it as recent adjacent work, not as a market competitor.
- verified: True

## OpsWeave: multimodal evidence compiled into a versioned, validated, approvable workflow (plus two unrelated namesakes) — SauravMukherjee44 (GitHub). Namesakes: slemens/opsweave (Sebastian Lemens, commercial ITSM) and godaylor/opsweave (incident playbook workspace, MIT) (GitHub. Repo created 2026-08-29; 18 commits whose timestamps run 2026-09-28 to 2026-10-03 at even ~7h23m intervals, and one commit adds a 'commit date rewrite utility', so the dates are likely rewritten; 0 stars; no license file)
https://github.com/SauravMukherjee44/OpsWeave
- Takes SOPs, policy PDFs, package photos, employee interviews, spreadsheets and OpenAPI specs and produces an immutable JSON workflow version that is not tied to any one orchestration engine. Node types are extract, retrieve, rule, agent, tool, approval, notification and terminal. A deterministic validator checks for unreachable nodes, missing terminal paths, undeclared tools, unsafe permissions, and consequential actions that lack required approvals. Extraction runs on Amazon Bedrock Data Automation and must match a JSON Schema; invalid output gets one repair attempt, then goes to a human review inbox that uses Step Functions callbacks. Stack: FastAPI on Python 3.12 (Lambda), Next.js with React Flow, and Terraform, Step Functions and DynamoDB on AWS. A deterministic 60-case evaluation matrix (standard, ambiguous, incomplete, adversarial) measures execution success, citation accuracy, escalation recall and unsafe-action rate. Its first use case is damaged-shipment claims. Namesakes: slemens/opsweave is a CMDB-centred ITIL ITSM product with a DAG topology, an SLA engine that inherits over the dependency graph, and 1,369 compliance controls. Its LICENSE file is a proprietary EULA and its README badge says 'Commercial'; an AGPL claim attributed to opsweave.de could not be re-checked because the domain did not resolve on 2026-10-13. godaylor/opsweave is an MIT, mostly Russian-language (RU default, EN toggle) playbook workspace with approvals and execution history, 8 commits.
- JETTAE: Of everything found, this is the closest architecture to JETTAE: LLM extraction, then a deterministic validator, then human approval, then a frozen versioned graph drawn in React Flow on a FastAPI backend. The difference is the domain and the meaning of the checks. OpsWeave validates whether a business workflow is executable. JETTAE validates whether an incident-response path holds up: escalation cycles, missing fallback channels or rollbacks, departed contacts, Korean 24h and 72h reporting steps, on-call fatigue, and rehearsals of absences and outages. It also adds Korean span grounding and a 0-100 readiness score. In Q&A the founder should say which OpsWeave they mean and be ready with one sentence on what JETTAE adds that a generic SOP-to-workflow compiler lacks: incident semantics and rehearsal. Because the commit history looks rewritten and the repo has 0 stars, present it as an architectural parallel, not as traction evidence.
- verified: True

https://github.com/rundeck/rundeck

- JETTAE: Rundeck shares the word 'runbook' but works on a different layer. It runs remediation scripts, whereas JETTAE checks whether the human and organisational response path written in the runbook document is complete. It does not compete with JETTAE's readiness layer. Integration: treat a Rundeck job ID or URL as an evidence node for 'rollback step exists and is executable', and flag runbooks that say 'roll back' without pointing to a job. It also makes a clean pitch contrast: Rundeck executes steps, JETTAE verifies the path works before anyone runs it.

Releases are slow (one release in almost three years), so it is a weak competitor and a possible downstream target: an approved JETTAE fix such as 'add fallback channel' could be exported as an st2 action or workflow stub. It is also useful in the pitch as proof that deterministic rules are an accepted ops pattern.

## Cortex Scorecards: Production Readiness and DORA Operational Readiness — Cortex (cortex.io) (Commercial internal developer portal; docs current 2026)
https://docs.cortex.io/standardize/scorecards/scorecard-examples
- Scorecards written in Cortex Query Language. Documented examples: `ownership.allOwners().length > 0`, `oncall.numOfEscalations() > 1` (at least two escalation levels, so there is a backup), `links("runbooks").length >= 1` (at least one runbook link), and a resolution-time threshold `oncall.analysis().meanSecondsToResolve < 3600` (the page does not use the term 'MTTR'). Built-in 'Production Readiness' (https://docs.cortex.io/solutions/production-readiness/configure) and 'DORA Operational Readiness' (https://docs.cortex.io/solutions/dora/configure) templates exist, the latter with Minimum, Established, Accelerating and Elite levels.
- JETTAE: The strongest commercial overlap with a 'readiness score'. The key difference: Cortex checks that a runbook link exists, while JETTAE checks what the runbook says. Is there an approver for the rollback? Does the escalation loop back on itself? Is there a fallback when the messenger is down? Do the 24h and 72h reporting steps have an owner? Then it rehearses those scenarios. Pitch line: 'Cortex asks whether a runbook exists; JETTAE asks whether it will work at 3 a.m. when the owner is on leave and Slack is down.' Possible integration: push the JETTAE score to Cortex as a custom data source or a check.
